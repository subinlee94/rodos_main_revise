# RODOS2 프로그램 수정 내역 — 교수님 보고용

> **목적:** 기존 RODOS2 IDE/서버를 ISO 22166 계열 정보 모델(교수님 PDF)에 맞게 쓰기 위해,  
> **이번 학기(세션) 동안 코드로 바꾼 부분**을 한곳에 정리한 문서입니다.  
> PDF 내용 자체를 구현한 것이 아니라, **원래 있던 프로그램을 어떻게 고쳤는지** 가 보고 포인트입니다.

---

## 보고 한 줄 요약

> 기존 RODOS2는 Controller·Software 중심으로 동작하도록 되어 있었고,  
> **Robot 모듈의 Registry 표시·업로드·캔버스 연결(SW 계승)·Execute 준비** 가 빠지거나 불안정했습니다.  
> ISO 스타일 **swAspects 연결 + ExecutableForm 기반 Execute** 흐름(`DEPLOY_EXECUTABLEFORM_FLOW.md`)에 맞춰  
> **UI·캔버스 저장·Registry·Execute 전 검증** 을 보완했습니다. **Docker Agent 호출부는 유지**했습니다.

---

## 수정 범위 지도 (어디를 건드렸는지)

```
[프론트 rodos2-ui]                    [백엔드 rodos2-server]
  Wizard (Available Modules)          Module 저장 (enum BIT32)
  IDE Sidebar / Workspace             Registry 업로드 + 로컬 fallback
  IDE Canvas (드래그·위자드)            SharedUserState 저장 (ref)
  Execute 버튼 전 검증                validate-execute API
```

## 6. 캔버스 — Software → Robot 계승 (Controller와 같은 패턴)

| 항목 | 내용 |
|------|------|
| **배경 (PDF/ISO)** | 복합 모듈은 **Software aspect를 참조(swAspects)** 하고, I/O·Services 등은 **연결된 SW IM**에서 가져오는 구조가 목표 |
| **기존** | Controller(사각형) 위에 SW 드롭 시 **linked 위자드** + `swAspects` 병합; **Robot(육각형)은 원만 붙고 위자드 없음** |
| **수정** | Robot 위 SW 드롭 시에도 **Robot linked 위자드** 오픈 (`wizardType: 'robot'`) |
| **수정** | `idnType.swAspects`에 SW moduleID(mID/iID) **참조만 추가**; Robot 부모 IM 필드는 **덮어쓰지 않음** |
| **수정** | IO/Services 단계에서 `/api/registry/module/linked-data`로 연결 SW 정보 **조회·표시** (기존 Controller와 동일 API) |
| **파일** | `useCanvasDragAndDrop.js`, `moduleLinkUtils.js`, `IDE.js`, `useWizardDialogState.js`, `WizardDialog.js` (기존 robot 분기 활용) |
| **보고 멘트** | “PDF에서 말하는 SW aspect 연결을 Robot에도 Controller와 동일한 위자드·swAspects·linked-data 흐름으로 확장했습니다. 전 필드 자동 병합은 하지 않았습니다.” |

## 8. Execute (Docker Agent) — Robot이 “안 되는 것처럼” 보이던 부분

| 항목 | 내용 |
|------|------|
| **문서 기준** | `DEPLOY_EXECUTABLEFORM_FLOW.md` — Execute는 **HW 위 SW 자식**만 실행; `getIM(ref)` → **ExecutableForm** → `DeployAgentApi` `:9999` |
| **기존 오해** | Robot Execute **코드 없음** (X) → **있으나** ref·target·구성 문제로 실패 |
| **수정 ①** | 캔버스 SW **`moduleID` → `ModuleInfo.ref`** 저장 (이름 lookup만 쓰지 않음) |
| **수정 ②** | Execute 전 **`GET /api/validate-execute`** + UI **alert** (Robot에 SW 없음, target 없음, Simulation 미설정 등) |
| **수정 ③** | `getHWModules`에 **target** 등 반환 (Mapping with HW 반영) |
| **안 한 것** | `ExecutorManager`, `DeployAgentApi` **변경 없음** |
| **파일** | `SharedUserStateService.java`, `SharedUserStateController.java`, `useModuleProgress.js`, `api.js`, `useCanvasState.js` |
| **보고 멘트** | “Agent 실행기는 문서대로 유지하고, Execute에 필요한 ref·HW Mapping·검증만 문서 §5.1·§7.4에 맞게 보완했습니다.” |

## 10. 수정하지 않은 것 (질문 받으면)

| 항목 | 이유 |
|------|------|
| ISO PDF 전 필드 자동 merge 표 | PDF에 드래그 시 필드별 규칙이 구현 수준으로 없음 → **swAspects + linked-data** 수준 |

| Composite만 있고 캔버스 SW 원 없을 때 Execute | Execute 대상은 **자식 SW ModuleInfo**만 |
| 원격 IIC Registry 항상 정상 동작 | 네트워크·서버 의존; fallback으로 완화만 |

## 11. 교수님 질문별 짧은 답변 스크립트

**Q. 뭘 목표로 수정했나?**  
> Robot·Software를 ISO 스타일 정보 모델로 연결·실행할 수 있게, 기존 Controller에 가깝게 Robot 경로를 맞췄습니다.

**Q. PDF 내용 그대로 구현했나?**  
> PDF는 SW IM 필수 항목(ExecutableForm 등)과 합성 개념을 정의합니다. 구현은 **swAspects 참조 + Registry linked-data + Execute ref/target** 으로 맞췄고, 필드 전체 자동 병합 표는 문서에 없어 팀 정책으로 제한했습니다.

**Q. Agent(9999) 쪽 손댔나?**  
> Agent 호출 코드는 **안 건드렸고**, Execute 전 **캔버스→SharedUserState→ref/target** 을 고쳤습니다.

**Q. Controller랑 Robot 차이?**  
> Execute는 둘 다 **HW 위 SW 원**이 대상입니다. Controller는 원래 linked 위자드가 있었고, Robot에 **같은 패턴을 추가**했습니다.

**Q. 데모 순서?**  
> Robot Registry → 캔버스 → SW를 Robot 위에 드롭 → (linked 위자드) → Mapping with HW → Execute.  
> 검증: `/api/validate-execute`

## 13. 발표·시연 시 권장 순서 (1~2분)

1. **Wizard** — Software IM 저장 되는 것 (bit enum 수정)  
2. **Registry** — Software / Robot 목록, Workspace 업로드  
3. **캔버스** — Robot 육각형 + SW 원, 드롭 시 **Robot linked 위자드**  
4. **Execute** — validate 후 실행 (또는 validate 실패 메시지로 “왜 필요한지” 설명)
