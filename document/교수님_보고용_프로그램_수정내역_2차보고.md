# RODOS2 프로그램 수정 내역 — 2차 보고 (교수님 보고용)

> **목적:** 1차 보고 이후, Robot/Controller 위자드에서 **연결 SW 정보 모델(Properties) 계승**이  
> 실제로 동작하도록 보완한 내용을 정리합니다.  
> **ISO 22166 PDF를 새로 구현한 것이 아니라**, 기존 RODOS 프로그램의 **데이터 읽기·표시 경로**를 고친 것입니다.

---

## 보고 한 줄 요약

> 1차에서 Robot에 **swAspects + linked 위자드** 흐름을 넣었으나, Properties 단계에서  
> **OS·Compiler·Libraries·Organization 탭이 비어 보이거나 Add만 되고 내용이 안 채워지는** 문제가 있었습니다.  
> 원인은 **WorkSpace XML 형식 차이**, **백엔드 XML 파싱 태그 불일치**, **API 직렬화 누락**이었고,  
> 이를 단계별로 수정하여 **연결 SW IM의 Properties를 Robot/Controller에 선택적으로 가져올 수 있게** 했습니다.

---

## 1차 보고와의 관계

| 1차 보고에서 한 것 | 2차에서 보완한 것 |
|-------------------|------------------|
| Robot IDnType에 SW/HW 선택 UI 추가 | 선택한 SW가 Properties에 **실제 데이터로 반영**되도록 수정 |
| 캔버스 SW 드롭 → linked 위자드 | 위자드 Properties에서 **linked-data API**로 SW IM 조회·병합 |
| `/api/registry/module/linked-data` 사용 | API 응답에 **compilerType·organization 등이 빠지던 문제** 해결 |
| Workspace 업로드·Registry 목록 | WorkSpace `Module Info` XML을 Registry에 **없어도** 목록·조회에 포함 |

---

## 1. WorkSpace Module Info — Registry 연동

| 항목 | 내용 |
|------|------|
| **문제** | WorkSpace에 올린 XML은 업로드는 되는데, 위자드 Available Modules·linked-data에서 **안 보이거나** 원격 Registry만 조회 |
| **수정** | `WorkspaceImService` 신규 — `.rodos/WorkSpace/Module Info/*.xml` 읽어 Registry 목록에 **병합** |
| **수정** | `getIM` 실패 시 workspace에서 **moduleID로 fallback** 조회 |
| **파일** | `WorkspaceImService.java`, `IMRegistryController.java` |
| **보고 멘트** | “교수님·팀이 WorkSpace에 둔 IM XML을, 원격 Registry 없이도 위자드에서 쓸 수 있게 로컬 경로를 붙였습니다.” |

---

## 2. Properties 계승 — 전체 탭 반영 (프론트)

| 항목 | 내용 |
|------|------|
| **문제** | Properties에서 연결 SW 항목 **Add** 시 Property 트리만 바뀌고, OS/Compiler 등 **다른 탭은 그대로** |
| **원인** | Add 핸들러가 `properties` 배열만 갱신; OS·Compiler 등은 **별도 state**인데 동기화 없음 |
| **수정** | `importPropertiesBundle()` — linked-data에서 받은 블록을 **모든 탭 state**에 한 번에 반영 |
| **수정** | `mergePropertiesBlocks()` — SW properties 전체(또는 일부)를 Robot IM에 **병합** (중복 제거) |
| **수정** | `linkedPropertiesMerge.js` **(신규)** — 필드명 정규화 (`osName`/`osname`, `opType`/`optype`, bit enum 등) |
| **파일** | `usePropertiesState.js`, `PropertiesPage.js`, `linkedPropertiesMerge.js`, `registryService.js` |
| **보고 멘트** | “ISO에서 말하는 SW aspect 참조 후, 사용자가 Add로 가져오는 방식을 Properties **전 탭**에 맞게 구현했습니다. 자동 전체 병합은 하지 않습니다.” |

---

## 3. linked-data API — Properties 직렬화 보완 (백엔드)

| 항목 | 내용 |
|------|------|
| **문제** | API 응답에서 `osType`은 나오는데 `compilerType`이 `{ osname: null }` 만 나옴 |
| **원인** | Jackson 기본 JSON 변환 시 `CompilerType.osName` 등 **getter/필드명 불일치**로 누락 |
| **수정** | `PropertiesMapSerializer` **(신규)** — Properties를 프론트용 Map으로 **명시적 변환** |
| **적용** | `IMRegistryController`의 `linked-data`, `model-data` 응답에 사용 |
| **파일** | `PropertiesMapSerializer.java`, `IMRegistryController.java` |
| **보고 멘트** | “연결 SW 정보를 JSON으로 넘길 때 compiler·execution 필드가 빠지지 않게 직렬화 계층을 추가했습니다.” |

---

## 4. WorkSpace XML 태그 형식 차이 — 파싱 수정 (핵심)

교수님·팀 WorkSpace XML과 프로그램 내부 상수가 **태그 이름이 달라** 파싱이 실패했습니다.  
**양쪽 형식을 모두 읽도록** 수정했습니다.

| 탭 | WorkSpace XML 예 | 기존 파서 기대 | 조치 |
|----|------------------|----------------|------|
| Compiler | `<compilerType>` | `<compiler>` | `Properties`에 `compilerType` 별도 바인딩 + getter에서 병합 |
| Execution | `<opType>EventDriven</opType>` | `<optype>` | `opType` 문자열 필드 추가 + enum 정규화 |
| Libraries | `<Libraries><Item name="..." version="..."/>` | `<Library>` 자식 태그 | `libraryItems` + Item 속성/자식 모두 지원 |
| Organization | `<organization><owner><moduleID>…` | 직렬화 시 항상 `{}` | `getOrganization()` 추가 + Map 변환 시 owner를 `mID-iID` 문자열로 |

| 파일 | `Properties.java`, `ExecutionType.java`, `Library.java`, `PropertiesMapSerializer.java` |

**단계별 확인 결과 (Navigation_Module 기준)**

| Properties 탭 | 수정 전 | 수정 후 |
|---------------|---------|---------|
| OS | (일부만) | Ubuntu / 64-bit / 22.04 ✓ |
| Compiler/Execution | 비어 있음 | OS Name, GCC, VerRange, EVENTDRIVEN ✓ |
| Libraries | 비어 있음 | 해당 XML에 Libraries **없음** → 비어 있음이 정상 |
| Organization | 비어 있음 | Owner module ID, OWNED ✓ |

**보고 멘트**  
> “WorkSpace에 있는 ISO 스타일 XML(`compilerType`, `opType` 등)과 예전 RODOS XML(`compiler`, `optype`)이 섞여 있어서, 파서를 **호환 읽기**로 바꿨습니다.”

## 5. hwAspects → swAspects 확장 (Controller/Robot + HW만 선택한 경우)

| 항목 | 내용 |
|------|------|
| **문제** | IDnType에서 HW(Controller)만 넣고 SW를 직접 안 고르면 Properties linked 목록 **비음** |
| **수정** | `linked-data` 요청 시 `hwAspects`에 연결된 부모 IM의 **자식 swAspects**를 펼쳐서 조회 |
| **파일** | `IMRegistryController.resolveLinkedSwAspects()` |
| **보고 멘트** | “Robot 아래 Controller만 연결된 경우에도, Controller IM에 등록된 SW를 Properties에서 가져올 수 있게 했습니다.” |

## 7. 수정하지 않은 것 (질문 받으면)

| 항목 | 이유 |
|------|------|
| Properties **자동 전체 import** | 1차와 동일 — 사용자 **Add**로 선택 가져오기 |

| ExecutorManager / DeployAgentApi | Execute Agent 호출부 **변경 없음** |

## 8. 교수님 질문별 짧은 답변 (2차)

**Q. 1차 이후 뭘 더 했나?**  
> SW 연결은 됐는데 Properties가 안 채워지던 걸, **XML 읽기·API·UI 병합**까지 이어서 고쳤습니다.

**Q. PDF랑 맞나?**  
> SW aspect 참조 후 Properties·OS·Compiler 등을 **연결 SW IM에서 가져오는** 방향은 PDF 합성 개념과 같고, **필드별 자동 merge 표**는 구현하지 않았습니다.

**Q. 왜 탭마다 따로 고쳤나?**  
> OS는 태그가 맞아서 먼저 됐고, Compiler/Libraries/Organization은 **XML 태그 이름이 달라** 파싱이 안 됐습니다. 원인 확인 후 단계적으로 수정했습니다.

**Q. 데모는?**  
> Robot 새 IM → IDnType에서 Navigation_Module(SW) 선택 → Properties → Add → OS / Compiler / Organization 탭 확인.

## 10. 시연 권장 순서 (1~2분)

1. **Registry / WorkSpace** — Navigation_Module 등 SW 목록 보임  
2. **Robot 위자드** — IDnType에서 SW 선택  
3. **Properties** — 연결 SW에서 항목 **Add**
